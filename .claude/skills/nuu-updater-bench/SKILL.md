# nuu-updater-bench

`dashboard-updater` をどのモデルで動かすのがよいかを、同じ初期データと同じ依頼文で測り直す。新しいモデルが出たときや、updater の定義を直したときに、前と同じ物差しで比べられる。

## 役割

あなた（最上位モデル）は、計測の進行役。分担は次のとおりで、汎用のサブエージェントへの委譲はない。

- 決まった結果になる処理（複製、状態の保存、採点、集計、片付け）は、すべてスクリプトが行う。毎回同じ結果になる必要があるため
- `dashboard-updater` の呼び出しは、あなたが Agent ツールで直接行う。その呼び出しが計測の対象そのもので、依頼文を一字も変えずに渡す必要があるため。間にほかのエージェントを挟むと、依頼文と同時に動く数がそろわなくなる
- あなたが自分で判断するのは、最後の報告だけ

## 入力

- 引数は比べるモデル（`haiku | sonnet | opus | fable`、1 つ以上）。省略したら `haiku sonnet`
- 利用者が一部だけ測り直したいと言ったときは、`prepare` に `--patterns 1,3,8` を付ける

## 使う道具

- `python3`（標準ライブラリだけ）: `scripts/bench.py` と `scripts/grade.py`。STEP 1〜4 で使う
- Agent ツール: STEP 2 で `dashboard-updater` を呼ぶ
- 検査と一覧の作り直しは、スクリプトがリポジトリの `hooks/dashboard-validate.py` と `hooks/dashboard-page.py` を読み込んで行う。MCP は使わない

コマンドはリポジトリのルートで実行する。`<RUN>` は作業用のフォルダーで、セッションの scratchpad の下の `nuu-updater-bench` を使う（リポジトリの中には置かない）。以下の `bench.py …` と `grade.py …` は、次の形の略。

```
python3 .claude/skills/nuu-updater-bench/scripts/bench.py --run-dir <RUN> …
python3 .claude/skills/nuu-updater-bench/scripts/grade.py --run-dir <RUN> …
```

## フロー

| STEP | 内容 | 実行者 |
|---|---|---|
| 0 | 始めてよいかを確かめる | 最上位モデル |
| 1 | 初期データをモデルごとに複製する | スクリプト |
| 2 | updater を流し、状態を保存する。空になるまで繰り返す | 最上位モデル（直接）とスクリプト |
| 3 | 採点と集計 | スクリプト |
| 4 | 片付け | スクリプト |
| 5 | 報告 | 最上位モデル |

## STEP 0: 始めてよいかを確かめる

- 対話なしの実行（`claude -p` など）なら、何もせずに止まる。`~/.claude` の下に書けないので計測できない
- `~/.claude/nuu/dashboards/` に `zbench-` で始まるものがあるかを見る
  - あって、`<RUN>/state.json` もある: 前回の続き。まず `bench.py done` を呼んで、終わっている呼び出しの状態を保存する。そのあと STEP 2 を続ける
  - あって、`<RUN>/state.json` がない: 止まって利用者に知らせる（ほかのセッションが計測中か、片付けが済んでいない）

## STEP 1: 用意する

```
bench.py prepare haiku sonnet
```

`~/.claude/nuu/dashboards/zbench-sNN-<モデル>/` に初期データを置き、検査を通して、進み具合を `<RUN>/state.json` に書く。終了コードが 1 なら、出力の理由を利用者に伝えて止まる（「立ち止まる基準」を見る）。

計測の間は、一覧に `zbench-*` の行が並ぶ。片付けで消えることと合わせて、利用者に一言伝えてから進める。

## STEP 2: updater を流す（最上位モデルが直接）

次を、`next` の出力が空の配列 `[]` になるまで繰り返す。

1. `bench.py next` を実行する。標準出力は JSON の配列で、要素は Agent ツールの引数（`description`、`subagent_type`、`model`、`prompt`）。終了コードが 3 なら新しい回ではないので、2 へ進まずに「守ること」の出し直しの扱いに従う
2. 配列の全要素を、1 つのメッセージでまとめて Agent ツールで呼ぶ。4 つの値はそのまま使い、`prompt` は一字も変えない（前置きや補足を足さない）
3. 全部の完了の通知を待つ
4. `bench.py done` を実行する。終わった呼び出しの状態が保存される

守ること:

- 1 回に出るのは 18 件まで（`--max` で減らせるが、受け付けるのは 1〜18 だけ）。同時に動かせるサブエージェントは 20 個なので、ほかの用途に 2 つ空けてある。同じパターンの全モデルは、同時に動く数をそろえるために同じ回に入る
- Agent ツールが同時に動かせる数の上限で弾いた呼び出しは、ほかが終わってから同じ引数で流す
- `done` の終了コードが 1 なら、出力に挙がった呼び出しが終わっていない。まだ動いているものは通知を待つ。失敗して終わったものだけを同じ引数で流し直し（引数は `next` がもう一度出す）、`done` を呼び直す。同じ呼び出しが 2 回続けて失敗したら、繰り返さずに STEP 3 と 4 へ進み、どの呼び出しがどう失敗したかを報告する
- `next` の終了コード 3 は、新しい回ではなく出し直し。流している最中の呼び出しのうち、終わっていたものは `next` が状態を保存し、標準出力には終わっていないものだけが出る。全部は流さず、`done` の終了コードが 1 のときと同じに扱う
- 通知が来ない呼び出し（再開したセッションには、前のセッションの通知が来ない）は、`done` と `next` が呼び出しごとに添える「記録の最後の書き込みから N 秒」で見分ける。5 分（300 秒）たっていれば止まったものとして流し直し、まだなら待ってから `done` を呼び直す。「記録がまだない」ものは流れていないので、同じ引数で流す
- 流し直した手順は、始まりが最も新しい記録で判定される。それが終わるまでは、以前に終わった記録があっても状態は保存されない
- updater の返事に「構成の見直しが必要です」や「最終状態が要る」とあっても、`dashboard-builder` を呼んだり、updater を呼び直したりしない。その返事が採点の対象になる
- 途中で止まっても、`done` と `next` で続きから流せる。会話の記憶ではなく `<RUN>/state.json` と保存した状態を正とする

## STEP 3: 採点と集計

片付けの前に行う（一覧から外す手順の採点が、いまの一覧を読むため）。

```
grade.py -v
bench.py stats --detail
```

- `grade.py`: モデルごとに「手順 N/M が全項目合格、項目 X/Y」と、不合格の項目
- `stats`: モデルごとの記録に残ったモデル ID、時間、1 回あたりの料金、差し戻し、失敗したツール呼び出し、トークン。完了とそれ以外の内訳、差し戻しのあった手順、呼び出しごとの返事の先頭
- どちらも、`done` と `next` が `<RUN>/state.json` に控えた記録だけを読む。あとで同じモデルを測り直しても、この計測の結果は置き換わらない。控えた記録のファイルがなくなった手順は「記録なし」と出て、ほかの記録では埋まらない

## STEP 4: 片付け

```
bench.py cleanup
```

名前が `zbench-sNN` か `zbench-sNN-<モデル>` のフォルダーだけを消し、一覧を作り直して、残りが 0 件かを確かめる。終了コードが 1 なら、残っているものを報告に書く。手で消さない。`<RUN>` の中身は残る（採点と集計をあとから見直せる）。

## STEP 5: 報告

結論（どのモデルが向いているか、差がどこに出たか）から書く。成果物は会話への報告だけで、リポジトリには何も残さない。次を入れる。

- モデルごとの表: 記録に残ったモデル ID、正しさ（全項目合格の手順と項目の数）、1 回あたりの時間、1 回あたりの料金、差し戻し
- 完了とそれ以外の差（時間、差し戻し）
- 返事の質で気づいたこと（`stats --detail` の返事を読んで。長さ、求めた内容を返しているか）
- 不合格の項目、流し直した呼び出し、単価がなく料金が「不明」のモデルがあれば、そのまま書く
- 注意: 手順ごとに 1 回ずつしか流していない／料金は記録のトークンからの推計／同時に流しているので時間は長めに出ることがある

ツールの結果で裏付けられることだけを書く。確かめられなかったことは、確かめられなかったと書く。

## パターン

`scenarios/base/` の初期データ 12 個と、`scenarios/prompts.json` の依頼文 38 個。採点の基準は `scripts/grade.py` の `checks()` にある。

| パターン | 手順 | 確かめること |
|---|---|---|
| s01 | 7 | 手順とパネルの更新、質問の追加、PR の掲載と状態の変更、中断と再開、回答つきの完了までの通し |
| s02 | 2 | 箇条書きではない報告の文章から、変化を読み取る。直ったテストを、止まっているものに残さない |
| s03 | 4 | 表に行を足す。止まっているものを足して外す。表のセルを最終状態にして完了 |
| s04 | 2 | 質問を 2 件足し、片方だけを回答済みにする |
| s05 | 2 | 成果物を 3 件足し、1 件の説明だけを直す |
| s06 | 3 | 進み具合の棒を進める（3 → 7 → 10） |
| s07 | 3 | 推移のグラフに点を足し、棒の値もそろえる |
| s08 | 3 | GitLab の MR を、下書きからマージ済みまで進めて完了 |
| s09 | 2 | 手順を途中に差し込む。手順の名前を変える |
| s10 | 4 | 文章のパネルを書き換える。中断、再開と同時の完了、一覧から外す |
| s11 | 3 | 決まっていない語彙を直す。最終状態が足りない完了では、推測で埋めずに残りを返す。受け取ってから完了 |
| s12 | 3 | 語彙を直す。https でない URL の項目を載せない。パネルの追加は断り、構成の見直しが必要と返す |

## 決まり

- 既定のモデル（`agents/dashboard-updater.md` の `model`、`~/.claude/nuu/settings.json`）は変えない。結果を見て変えるかは利用者が決める
- `zbench-*` 以外は消さない。消すのは `cleanup` だけに任せる
- 依頼文、初期データ、採点の基準は、計測の途中で書き換えない
- 単価が変わったときは `resources/rates.json` を直す

## 立ち止まる基準

次のときだけ止まり、利用者に知らせる。ほかは確認を挟まずに最後まで進める。

- 対話なしの実行だったとき
- `zbench-*` が残っていて、続きを流せる state file がないとき
- 初期データが検査を通らないとき（データの形が変わった合図。`scenarios/base/` を作り直す必要がある）

## 完了条件

- [ ] 全モデルで、対象の手順がすべて流れている（`next` が `[]` を返した）
- [ ] 手順ごとの状態がそろっている（`grade.py` に「まだ」の行がない）
- [ ] 記録に残った実際のモデル ID を報告している
- [ ] `cleanup` の結果が、残っている `zbench-` 0 個、一覧に残っている `zbench-` 0 件
- [ ] 既定のモデルを変えていない
