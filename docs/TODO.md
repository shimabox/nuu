# 今後の検討

## トークン量を正確に出す（OpenTelemetry）

- 今: `hooks/dashboard-usage.py` が会話の記録（`~/.claude/projects/`）から集計している。記録には、サブエージェントの応答の確定した出力トークンが残らないことがあり、その分は少なめに出るため、目安と注記している
- 案: Claude Code の OpenTelemetry（`CLAUDE_CODE_ENABLE_TELEMETRY=1`）で、API リクエストごとのトークン量と料金を受け取る
- 検討すること
  - 取れる項目の正確な名前と、サブエージェントの分を区別できるか（公式ドキュメントで確かめる）
  - 受け取り先（OTLP のコレクターなど）が別に必要になる。常に動かす仕組みを利用者に求めるか、今の集計と選べるようにするか
  - ダッシュボードを用意し始めた時刻で区切る方法
  - 受け取った値をダッシュボードに渡す方法（今の `.usage.js` の形をそのまま使えるか）

## 危ない既定の対応で進んでいる質問だけを通知する（Jev）

- 背景: 利用者の判断が必要になっても止まらず、既定の対応で作業を続ける。既定の対応に、取り消せない操作や影響の大きい操作が含まれていると、気づかないまま進んでしまう。取り消せない操作は承認を待つルールがあり、これはその見落としを補う
- 案: dashboard-updater が質問を追加したら、フックのスクリプトが質問と既定の対応を TypeSafe の Jev に送り、次を判定する。しきい値を超えた質問だけをダッシュボードと一覧で目立たせる
  - 既定の対応に、取り消せない操作や外部への公開が含まれるか（Noul）
  - 既定の対応で進めた場合の影響の大きさ（Score。レベルは程度ではなく状況で書く）
- 検討すること
  - API キーは macOS のキーチェーンに置き、フック専用の固定ラッパーから実行時だけ渡す
  - 日本語は精度が落ちやすいので、実際の質問文で確かめてからしきい値を決める
  - しきい値を決めたら、モデルのバージョンを固定する
  - 送るのは質問と既定の対応だけにする。本物の質問文で試すときは、送る内容を確認してから行う
  - 通知の手段は利用者の環境に任せる。nuu は、危ない質問があることを判定結果として残し、通知に使えるようにするところまでを受け持つ

## 見送ったもの

### dashboard-updater の反映漏れを Jev で確かめる

更新の依頼と、書き換える前後の JSON の差分を Jev に渡し、依頼がすべて反映されたかを判定する案。次の理由で見送った。漏れが目立つようになったら、改めて検討する。

- 改善後の dashboard-updater は、測定した 3 回の更新で漏れがなかった
- ダッシュボードは作業の正本ではなく、漏れても次の更新で直ることが多い
- Jev は何が漏れたかまでは返せないため、直させると読み直しが増え、軽いモデルに任せた効果が薄れる

一覧の行の数字（完了した手順の数、未回答の質問の数など）がダッシュボード本体と一致しているかのように、コードで確かめられるものは、Jev を使わずにコードで確かめる。
